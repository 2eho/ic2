# 13 · 核验与迭代

> 回应 Issue 的两条要求：
> 1. 「实现之后核验功能和设计，持续迭代并核验，直到达到可上线水准」；
> 2. 「持续对抗并解耦，直到达到无系统漏洞水准」。
>
> 本文给出**可执行的核验体系**：谁能判定「通过」，判定依据是什么，不通过怎么办。

## 0. 先对齐一个前提：「无系统漏洞」不等于「零缺陷」

任何非平凡系统都存在未知缺陷。工程上可达成的目标是：

> **已知边界全部有对抗用例；未知缺陷的爆炸半径被隔离在可恢复的范围内。**

对应两条机制：

1. **覆盖面**：`11-boundary-and-adversarial.md` 的每条对抗都有自动化用例，且新功能必须补用例。
2. **可恢复**：任何单点故障（进程、插件、Provider、实例）不会导致数据丢失或不可恢复状态（INV-1..10）。

因此本项目的验收语言是「不变量成立 + 已知对抗全绿 + 恢复演练通过」，
而不是「没有 bug」——后者不可证，写进验收标准只会导致自欺。

### 3.2 对抗用例即回归

`11-boundary-and-adversarial.md` §3 的 ATK-01..22 是**发版门禁**，不是「有空再补」。

规则：

- 新功能 PR 必须至少新增 1 条对抗用例（PR 模板必填）。
- 修复线上缺陷时，先写失败用例，再修代码（禁止「先修后补」）。
- 对抗用例跑在「故意制造极端输入」的分支，不允许 mock 掉被测逻辑。
- **用例必须能失败**：改回缺陷实现后用例要变红。写完用例应实测这一点
  （本轮四个用例在修复前都是结构性必红/必绿，靠实测才发现）。
- 对抗用例跑在**真实依赖**上：冲突/离线类用例必须打在真实服务端进程上，
  不能用内存替身——本轮「SQLite 时间列扫描」与「baseVersion 语义」两个缺陷
  恰恰只在 SQL 路径上存在，内存替身跑一万遍也不会红。

### 3.5 假绿通道（本轮新增的门禁）

「没跑」必须表现为失败，不能表现为通过。以下四类形态在 CI 里都曾经把红变绿：

| 形态 | 后果 | 门禁 |
| --- | --- | --- |
| e2e 拿不到后端 → `test.skip` | 9 条对抗用例空转，CI 全绿 | `check-no-silent-skip.mjs`（e2e 禁止无条件 skip） |
| e2e 引入不存在的模块 → 永久 skip | ATK-18/19 从未真正执行 | 同上 + 挂载点就绪断言 |
| `cmd \|\| echo 跳过` | 工具缺失被当成检查通过 | 同上（Makefile 层）+ `preflight` 显式失败 |
| CI 里 `make <gate> \|\| true` | 门禁失败被吞 | 同上（`.cnb.yml` 层，白名单逐条列） |

配套纪律：
- 条件跳过必须写 `ALLOW-CONDITIONAL-SKIP: <理由>`，理由要说明**什么条件下才该跳**；
- 白名单必须是**精确匹配的整行**，不能用「注释里出现了某个词」这类模糊判断——
  实测过，模糊判断会让 `make parity || true` 因为附近恰好有「上游巡检」的注释而被放行。

### 3.6 工具链可用性（本轮新增）

工具在不在必须被**探测**，不能被假设。自托管 Runner 与托管 Runner 的工具集不同，
假设会导致「本地绿、CI 红」，或更糟的「CI 绿、其实没跑」。

- `scripts/toolchain-probe.mjs`：逐项探测并给出安装方式；必需项缺失即失败。
  工具解析顺序是「显式候选目录 → PATH」，`prettier` 显式从 `web/node_modules/.bin`
  解析——否则 CI 的 `gen-check` 步骤永远找不到它（该步骤不会注入该目录）。
- `scripts/doctor.mjs`：环境体检（工具链 / 契约生成物 / Go 可构建 / 依赖 / 可写性）。

两个已修复的具体问题：
1. Node 的 `spawnSync('gofmt', ...)` **不查 PATH**（先按无扩展名查找再补 `.exe`），
   因此裸名调用必然 ENOENT。旧代码把它降级成「不格式化就写盘」，于是
   `make gen` 写脏工作区、`gen-check` 永远红。
2. `prettier` 被 `gen-contracts` 依赖，却从未声明在 `web/package.json` 里，
   仅靠 `npm exec` 的隐式下载掩盖——CI 里必红。

- `go vet` / `staticcheck` / `govulncheck` 零告警（高危零容忍）。
- `tsc --noEmit` 零错误；`eslint` 零 error。
- `npm audit` 高危零容忍，中危需登记豁免理由与期限。
- 单文件 >500 行在 PR 说明中解释；`features/*` 禁止跨目录深层 import（用依赖检查脚本强制）。
- 生成物（`shared/api/generated/*`）必须与 `contracts/openapi.yaml` 一致（CI 重跑 `make gen` 后 diff 为空）。

### 4.1 里程碑验收标准（可执行，不含形容词）

| 里程碑 | 验收标准 |

| M3 | 单节点批量产出 4 张图且可切主结果、无隐藏父子节点；RunPanel 显示 token/张数/秒/成本；超限有明确错误码；ATK-17 绿 |

| M7 | 压测达标；备份/恢复演练通过（含全量导出回灌）；密钥轮换演练通过；文档站上线；`v1.0.0` 发布 |

### 4.2 故障演练（每里程碑一次，M7 强制）

| 演练 | 操作 | 期望 |
| --- | --- | --- |
| 进程崩溃 | Run 运行中 `kill -9` 服务端 | 重启后任务恢复或明确失败；无重复扣费；不变量成立 |
| DB 不可用 | 断 DB 连接 30s | 读请求降级提示；写请求明确失败不产生脏数据；恢复后自愈 |
| Blob 不可用 | 断 MinIO | 图片展示占位；上传失败明确报错；不影响文档编辑 |
| Redis 不可用 | 集群模式断 Redis | SSE 退化为单实例；队列暂停并告警；恢复后续跑 |
| 磁盘写满 | 填满数据盘 | 拒绝新上传并告警；不损坏已有数据；编辑仍可用 |
| 时钟回拨 | 回拨服务端 1h | 租约/限额不误判（用单调时钟 + DB 时间） |
| 上游 429 风暴 | Provider 持续 429 | 队列退避、限额生效、用户可见「被限流」而非「失败」 |
| 恶意插件 | 装一个尝试越权/发外网请求的插件 | 全部被拒并审计；主页面不受影响 |
| 备份恢复 | 从昨日备份恢复 | 数据一致；op 日志可重放得到同文档（INV-1） |
| 密钥轮换 | 轮换主密钥 | 旧密文可读（双密钥期）；轮换后新写入用新密钥；无中断 |

### 4.3 可观测核验

- 任意一次用户可见错误，都能凭 `traceId` 定位到 HTTP → graph → exec → provider 的完整链路。
- 每个 Run 有：状态、耗时、每 Step 的 attempt 明细、usage、错误分类。
- 仪表盘：SSE 连接数、队列深度与延迟、Run 成功率、Provider 错误率/延迟、资产存储量、DB 连接池。
- 告警：队列积压、错误率突增、磁盘水位、SSE 连接泄漏、GC 失败。

## 5. 持续迭代机制

### 5.1 迭代触发源

| 来源 | 处理 |
| --- | --- |
| 上游 `change-report`（§12） | 分类为契约/边界/功能/安全，进迭代队列 |
| 对等矩阵未完成项 | 按里程碑排期 |
| 死角表复审触发 | 触发时升级为正式需求 |
| 用户反馈 / Issue | 评估价值与代价，进队列或明确拒绝 |
| 对抗用例失败 | P0，立刻修 |
| 性能预算退化 | CI 失败，必须解释或优化 |

### 5.2 迭代节律

```
需求 → 设计评审（L1 检查单）→ 实现（含对抗用例）→ CI（L2）→ 里程碑验收（L3）→ 灰度 → 全量
                                                              ↓
                                                    复盘 → 更新设计文档与死角表
```

**纪律**：

- 设计文档先改，代码后改（与上游同步同序）。
- 每个迭代结束必须更新 `10-parity-matrix.md` 的进度与 `11` 的死角表。
- 不允许「代码已经上了但设计文档没写」。
- 每个 release 在 `docs/upstream/sync-log.md` 记录当时对应的上游版本。

### 5.3 上线水准的定义（本项目的 Done）

一个功能算「可上线」，当且仅当：

1. 在对等矩阵中状态为 `done`（或有明确 `dropped` 理由）。
2. 涉及的不变量有测试证明。
3. 新增边界有对抗用例且全绿。
4. 性能预算未退化。
5. 错误有稳定 code 与 i18n 文案。
6. 有可观测（日志字段、指标、trace）。
7. 文档（本目录）已同步。
8. 故障演练未暴露该模块的不可恢复路径。

任一不满足 → 状态为 `wip`，不算完成。**这条是用来对抗「差不多就行了」的。**

## 6. 快速核验命令（意图）

```bash
make doctor         # 环境体检（工具链/依赖/可构建性）
make toolchain-probe # 工具链逐项探测（自托管 Runner 适配）
make gen            # 从 contracts 生成 Go DTO 与 TS 客户端，并校验已提交
make lint           # vet + 架构约束 + 假绿通道检查（check-no-silent-skip）
make test           # 单测 + 前端单测 + 桥接器单测（含对抗用例）
make e2e            # 起真实服务端进程 + Playwright 主链路（含 15 条 e2e）
make perf           # 性能预算校验
make parity         # 对等矩阵覆盖率报告
make boundaries     # 边界常量与文档一致性校验（internal/graph/limits.go ↔ docs §2.1）
make sec            # 脱敏 / SSRF / 插件权限 / 资产隔离 / 上游幂等 / 仓库卫生
make drill          # 故障演练（本地可跑的子集）
make upstream-radar # 上游雷达自检（产物齐备 + 探针从离线夹具抽到契约面）
make check          # 上面除 e2e/perf/tsc 外的全部（CI 用这一个）
make check-all      # check + tsc + e2e-build + e2e + perf
```

**`make e2e` 的形态**：它先 `scripts/e2e-stack.mjs start` 起一个**真实的服务端进程**
（独立临时数据目录、固定密钥、同源托管构建产物），再打 Playwright，最后自动清理。
不用 `httptest` 顶替的原因：ATK-10（沙箱）要看真实浏览器与真实 origin 语义，
ATK-12（离线恢复）要能真的断网，同源托管只有真进程才有。

`make boundaries` 是关键一条：**边界常量只允许有一处真源**（`config/limits.go`），
文档中的数值由脚本校验，避免「文档写 30 秒、代码是 60 秒」。
